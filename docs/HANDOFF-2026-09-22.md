# PART 1 — THE ONE NUMBER THIS SESSION IS ABOUT

`racecast/pool_view.py` recovers a constant `C` per pool: the 5,000m-equivalent
time of a pool-average member. Measured on the live corpus:

```
C(hs_m)  = 1211.5   = 20:11 for 5K
C(pro_m) = 1553.1   = 25:53 for 5K      <- both at a 5000m anchor
```

**The professional pool's average member runs a 25:53 5K.** It is not lightly
contaminated; it is dominated by people who are not professionals. And because
`speed_rating` is pool-relative, every one of them drags the pool's 100-anchor,
so the contamination does not merely mis-file those athletes — it **bends the
rating of every genuine professional measured against them**.

Everything in PART 3 is downstream of that number.

Files: `engine/pool_resolve.py` (the standard + the veto),
`engine/build_pro_ability.py` (builder), `engine/pro_ability.py` (the one

### Three things that are load-bearing and non-obvious

**1. The stored `normalized_time` cannot be used.** `targetFor` gives every pool
a different anchor — 5000 for hs and pro, **8000 for college men**, 6000 for
college women, 3200 for ms. Testing a college man's stored number against 840
asks him for a 14:00 *eight* thousand. Every mark is re-expressed from the RAW
time on one curve, `hs_<gender>` at 5000m — which is also what keeps the table
out of a loop with the pooling it feeds.

**2. Tri-state, and `None` is inert.** A missing table, an empty load, a row
with no season: all leave pooling exactly as it was. Reading absence as "not
fast enough" on an unbuilt table would demote every professional in the corpus
on the first run after a schema change.

**3. The pace band (`5b74717`).** The first `--dry-run` over the real corpus
listed these as the fastest athlete-seasons in the database:

```
17494297  2023  F   0:00.2
25737720  2010  F   0:12.5
```

`nt = t * k(d)` reaches 0.195s at `d = 4,700,000` metres and 12.1s at
`d = 100,000`. Those rows carry distances of 4,700km and 100km, and 23 of the
30 fastest were the same 2023 cluster. They pass `streamResults` because its
band is on the STORED `normalized_time`, which was written with a *different*
distance than `dist_m` now carries — **the disagreement only shows when the mark
is re-expressed**, so the builder is where it has to be caught. Banded with
`normalize_distance.poolBandFor` (PACE_FLOOR 0.12 s/m → 600–3600s at 5000m),
the engine's own rail. The rejects are **reported with their `dist_m` and
`time_seconds`**, because a corrupt distance outlives this gate — see PART 4.

### Where the bar lands (measured on the live spline, not asserted)

```
men, 14:00                     women, 15:30
  800  1:47 -> 13:58 PASS        800  1:56 -> 15:01 PASS
  800  1:50 -> 14:22 fail        800  2:00 -> 15:32 fail
  Mile 4:00 -> 13:56 PASS        Mile 4:20 -> 15:00 PASS
  10000 28:30 -> 13:32 PASS      10000 31:30 -> 15:00 PASS
```

The 800 cut is ~1:47.5 for men, ~1:59.5 for women — about the floor of
professional half-lap racing. Field events and everything under 800m are never
rated (`_tfQuery` excludes them), so no sprinter or thrower is judged by a 5K.

**Dry run, whole corpus:** 64.4M rows, 13.7M athlete-seasons, **14,779 able**
(11,795 men, 2,984 women) = 0.108%. Over a ~25-year corpus that is ~470 men and
~120 women a year, the right order once international rows are counted.

## The athlete header's HS-equivalent (`e864bb3`)

Owner: *"athlete rating for the pro pool ppl is completely fucked up for
hs-equivalent. However hs-equivalent now works for indiv races."* Both halves
were the diagnosis. Races are right because `stampHsRatings` gives each race
*its own pool's* factor. The header used `seasonFactor(races)` with no filter —
the median over the WHOLE CAREER — on a number from `athlete_ratings`. For a
career spanning pools that is a median of 1.00 and 0.78: the factor of no pool
the athlete ever raced in.

Pro athletes take that branch **always** — `athlete_season` comes from
`ranking_results` and `isRankablePool` refuses `pro_*`, so they have no season
row by construction. Fixed with `repFactor(pool)`, which is exact (hsFactor is
one number per pool). The season branch one line up had the same defect and was
closed with it; the season *block* below the header keeps its median and now
says why (its number is not a per-pool quantity).

## The pool-constant sampler (`247b6e0`)

`_CONST_SQL` took 1,500 `ranking_results` rows **inside a CTE**, then joined and
dropped the unrated ones. An unordered `LIMIT` over the biggest pool returns a
correlated physical slice, and high school track is mostly sprints and field
events. Zero of 1,500 survived, both genders. Reproduced on Postgres 16: 0 rows
for the big pool, 1,500 for a small one, 1,500 once the filter runs first.

**The damage was not local.** `hsFactor` combines the per-sport *ratios*, so
losing the hs TF constant cost every OTHER pool its TF ratio — the whole table
read `1 sport ratio(s)`.

Fixed by reusing the query already in the file: `rating_pool` is stamped on
every rated row, so it needs no join. It is now the retry for any pool that
samples thin, not just pro (hence `_STAMPED_CONST_SQL`, no longer `_PRO_`). The
primary still runs first — it is cheap on a rare pool; the retry is instant on a
common one.

## The grass-gap column (`58aa7db`)

Both constants for a pool are at the same anchor, so `ln(C_XC / C_TF)` is that
pool's own measurement of what grass costs — and `bracket_engine.XC_TRACK_GAP`
is `ln(1.06)` = 5.83%, a **definition** that could never be measured there
because the seasons do not overlap.

```
ms_m       3.31%      college_m   -2.02%   <- BACKWARDS
ms_f       3.47%      college_f   -2.24%   <- BACKWARDS
hs_m       5.12%      pro_m       -0.43%   <- BACKWARDS
hs_f       4.98%      pro_f        0.13%   <- far from 5.83%
```

hs corroborates the defined gap to half a percent. A negative gap is physically
impossible — it says a pool's track population is slower than its cross-country
population at the same anchor.

# PART 5 — HAZARDS, AND FOUR THINGS I GOT WRONG

## `XCP_TEAM_POOL` is OFF and route 2 is dead

`speed_ratings.loadProTeams` returns an **empty set** unless `XCP_TEAM_POOL=1`,
deliberately since 2026-09-19. Nothing in `deploy/solve_env.sh`,
`run_pipeline.ps1` or `overnight_fit_pool_solve.sh` sets it. The **site never
passes `team_pro` at all** — neither `build_ranking_results`, `panels` nor
`fill_ratings` names the argument.

`engine/build_team_pool.py` is in **no chain**. If the flag is ever switched on,
that builder must run before `07_pack` or the table is stale.

## What I got wrong, in order

1. **The XC level pin (`eabc3e8`) was my regression.** Under `gauge=flat400`
   the go-live's `trackPopulationShift` is skipped, so both sports sit at their
   own zero and the relationship is carried by the athlete term. Adding +5.83%
   to every XC cell moved one sport with nothing to absorb it. `xc_reference.py`
   says this outright and I read it without hearing it. Reverted in `bfdd06a`;
   the shift is kept, tested, and off by default.

2. **The same pooling bug shipped twice.** I fixed `build_team_pool.classify` on
   the 20th and declared it fixed; `pool_resolve`'s `team_has_pros` was a second
   implementation excluding only college. `pool_resolve`'s own header warns
   about exactly this.

3. **I read a dead route as a live one (`0c19b95`).** `diag_pro_routes`' route-2
   listing — Japan 5,468 athletes, United States 5,189 — is a population the
   rule *could* claim and currently claims none of. The header's caveat was
   about the majority gate and did not cover a route switched off at the source.
   The diagnostic now reads the flag and says which state it is in.

4. **I tightened `team_has_pros` for symmetry and had to put it back.** The two
   routes are not symmetric: route 2 sweeps everyone who ever raced for the
   team, route 3 only fires behind `clubSeason`'s majority gate — the owner's
   own 2026-09-16 condition. `tests/test_team_level_pool.py` caught it.

Also: one of my own tests from 09-20 failed on a *correct* change because it
pinned a literal source string. It calls the function now. That is the third
time in this repo a test has argued for the thing it was written to check.
