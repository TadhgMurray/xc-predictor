## 1. RUN THIS FIRST — all the logos are gone again

`loadCrests` (racecast/school_logo.py:144) hides a crest **exactly four
ways**, so one query says which:

    /srv/venv/bin/psql "$XCP_DB" -c "SELECT count(*) rows, count(path) with_path, count(*) FILTER (WHERE shared) shared_hidden, count(*) FILTER (WHERE lower(override)='none') off, count(DISTINCT sha) distinct_sha FROM school_logo WHERE path IS NOT NULL;"

Read it like this:

| what it shows | what it means |
|---|---|
| `shared_hidden` ≈ `rows` | the sweep marked everything shared. `distinct_sha` will be far below `with_path` — crests collapsed onto identical bytes, 4+ schools per image (`SHARED_MIN`), and `markShared` hid them all. |
| `with_path` ≈ 0 | rows lost their `path` — a scrape wrote NULL over it |
| `off` high | overrides set to `'none'` |
| all four look fine | then it is the **disk**: `loadCrests` skips any row whose file is not on disk (`pathFor` + `os.path.exists`). Check `ls "$XCP_LOGO_DIR" \| wc -l` against `with_path`. |

⚠ **The most likely culprit, and it would be mine.** `--reground` rewrites the
PNGs and updates `sha`. If keying the grounds off made many crests
byte-identical, the *next* `markShared` sweep sees 4+ schools per sha and hides
them — and `markShared` runs in the main scrape path, which `anet_teams` calls.
`regroundAll` itself never touches `shared`, so the reground alone cannot have
done it; a scrape afterwards can.

**If `distinct_sha` is far below `with_path`, that is the answer.** The
unblocking move is `UPDATE school_logo SET shared = false` and then decide
whether the collapse is real (it might be — many anet mascots are genuinely the
same placeholder). Do not re-run the sweep until the sha collisions are
understood.

## 2. The World Athletics picture on Lawrence HS

**The scraper is not inventing it — the address book is wrong.** Candidates come
from `school_website` (built by `build_school_websites.py`); the scraper fetches
that URL and takes whatever the page *declares* as its mark (`apple-touch`,
manifest, tile, `og:image`, `rel=icon` — see `KINDS`). Point it at the wrong
domain and it faithfully returns that domain's logo. Confirm with:

    /srv/venv/bin/psql "$XCP_DB" -c "SELECT school, state, url, direct_logo FROM school_website WHERE school ILIKE '%Lawrence%';"

**The only defence in the code today is `markShared` (`SHARED_MIN = 4`)**, which
hides an image worn by 4+ schools. A generic mark on 1–3 schools slips through.

**The real fix, not written:** refuse a crest whose host does not plausibly
belong to the school — the registrable domain should contain a token of the
school name, or be a known district/state host, or the row should be dropped
rather than trusted. `_isSocial` already does exactly this shape of check for
social hosts; this is the same guard against generic-sports hosts. **Until that
exists, expect junk crests from wrong addresses.** This is the single highest
value logo task left.

## 4. The truncation fix (done, needs re-extraction)

The horizon twin's *truncation* was never the problem — `MIN_KEPT_RACES` is
already 2 and the window is sampled feasibly. **The draw was.**
`weeks = lo + random()**skew * (hi - lo)` with `HORIZON_GAP_SKEW = 1.0` is
uniform over a window whose upper bound is the gap back to the athlete's
*second* race — which, for the one- and two-season athletes who make up most of
the corpus, sits just under a year. Hence 52.1 weeks max and an empty 104w+
band.

- `HORIZON_GAP_SKEW` 1.0 → **0.5**: favours the long end of each athlete's own
  window. Same twin, different cut, no extra cost.
- **`_horizonLongTwin`**, a third generator drawing in [104, 208] weeks. Returns
  `None` for almost everyone by design, so rate 1.0 and all are kept.
- The extraction now **warns when zero two-year twins were produced**, because
  their absence is invisible in the horizon count — which is how it got past the
  last run.

**Nothing changes until re-extraction**, which is already pending for ISSUES G.
Fold them into one run. Then re-run `scripts/diag_calibration.py` and check the
104w+ and 208w+ bands: if they read LOW, the projection should be capped back to
52 weeks (`PROJECT_WEEKS` in `racecast/build_recruit_projection.py`).

## 5. Does the recruit projection use the model? Yes

`build_recruit_projection.py` → `_predictTimes(cur, ids, manual target 52 weeks
out)`. A rating is `100 × pool_mean / adjusted_time`, a **reciprocal**, so the
predicted time over the model's own baseline IS the rating multiplier — the pool
mean cancels and nothing is looked up. Ranked on the **residual** against others
starting at the same rating, because everybody at 80 is projected to gain more
than everybody at 115.

    /srv/venv/bin/python racecast/build_recruit_projection.py --dry-run --limit 500

prints the top ten per pool. Pipeline step `10f2_projection`; exits clean with
no model, and the search falls back to the rating sort while the table is
absent.

## 6. Calibration passed — the numbers, so a retrain can be compared

cover68 0.664–0.695 (target 0.683), cover90 0.883–0.901 (0.900), err/sig
0.796–0.842 (√(2/π) = 0.798), **spread 0.97–0.99**. Full table in
`docs/PLAN-2026-09-16.md` §7.

★ **`spread` is the headline.** The model is *not* shrinking everyone toward the
pool mean at a year out, which is the failure that would have made the
underrated-recruits list noise however good the coverage looked.

Shipped on the back of it: the **Win** column and the score-range hover on the
predictions page, `/api/predict/lineup` (endpoint only, **not wired to a
page**), and the three `proj_*` recruit sorts.

! **`team_rho = 0` is a floor, not a measurement.** Within-team correlation has
never been measured here, so the published `score_sd` is the *narrowest* the
spread can honestly be. Measuring it from historical races is a real task.
