## What was slow, and why

**The one cause behind most of the timings: eight sync workers.** gunicorn
runs 8 sync workers with a 60 s timeout. A handful of 30-60 s statements
(the four below) occupy all eight, and every other request waits in the
queue. That is why the sweep saw a `400` for a malformed board request (no
database work at all) take 31-33 s, and the static `/rankings` shell 34 s.
Fix the slow statements and the queue goes with them.

1. **`/api/rankings` ability board, `sort=best`** (51.8 s; also
   `/rankings/:sport/:pool/:state`). With the year filter at "Any", the
   ORDER BY is `best_rating DESC NULLS LAST, mean_rating DESC, person_id`
   after `pool = ? AND sport = ?`. The only best-rating index is
   `as_board_best_idx (pool, sport, year, best_rating ...)`, with `year`
   between the equalities and the ordering, so Postgres bitmap-scans every
   season of the pool from the heap (millions of rows for hs_m) and
   top-N-sorts them for one page. The `pageThenName` change already moved
   the name lookup after the cut; the sort itself remained.
   **Fix:** `as_pool_sport_best_idx (pool, sport, best_rating DESC NULLS
   LAST, mean_rating DESC, person_id)` and `as_pool_best_idx` (the same
   without sport, for `sport=both`). Plan becomes an Index Scan reading
   offset+limit+slack rows: 123 buffers on a 2.4M-row stand-in, vs. a scan
   of the whole pool.

2. **`/athlete/:id`** (up to 55 s). The "XC half" counts each race's place
   with a lateral over the race's field: `meet_id, div_id, source,
   time_seconds, result_id, status, school`. The index planned for it,
   `idx_results_meet_div_place (meet_id, div_id) INCLUDE (time_seconds,
   school)`, lacks `source`, `result_id` and `status`, so every competitor
   of every race is a heap fetch: a 70-race career is tens of thousands of
   random reads, which on a cold cache (pipeline running) is the 55 s.
   On top of that, nothing in the pipeline vacuumed `results`, and the
   go-live rewrites it, so even a covering index fell back to the heap.
   **Fix:** `idx_results_meet_src_cover (meet_id, source, div_id) INCLUDE
   (time_seconds, result_id, school, status)` (index-only, 0 heap
   fetches), and pipeline step 18c vacuums `results` and `results_tf`.

3. **`/race/xc/:meet/:div`** (63 s on `SELECT source, count(*) FROM results
   WHERE meet_id = ? ... GROUP BY source`). `idx_results_meet (meet_id)`
   finds the rows, but `source` is only in the heap: one random read per
   row of the meet. And a race view ran it up to three times (the pick, the
   canonical's bare pick, the `?r=` redirect test).
   **Fix:** the same covering index (source is in the key: index-only, 29
   buffers vs. one read per row on a shuffled stand-in) and
   `meet_sources` memoised per request.

4. **Cache fan-out from `?r=` links.** Every race and XC meet link on an
   athlete page carried `?r=<result id>`. The edge caches by full URL, so
   each race page existed once per finisher who linked to it, every click
   on one was a MISS, and each ran the 63 s statement (three times) only
   to 302 back to the bare URL. The pin only matters when two feeds share
   the meet id. **Fix:** the athlete page probes, per race, whether
   another feed holds that meet id (two index probes on the new index);
   if not, the link is the bare URL plus `#r<id>`, exactly where the 302
   landed. Multi-feed meets, and TF meet links (their page reads `?r=` for
   its scroll anchor), keep `?r=`. The probe only runs once the index
   exists, so deploying the code first changes nothing.

## Caching headers

Headers were already right (no Set-Cookie, `Vary: Accept-Encoding`, pages
and board APIs public with `max-age=300, s-maxage=900`; the edge does HIT
them). What kept the hit rate low: a 15-minute edge TTL over a very long
tail of URLs, the `?r=` fan-out above, and slow origin answers that time
out (a 504 is never stored).

- `stale-if-error=86400` on every public response: when gunicorn times out
  or the swap's 503 is up, Cloudflare may serve the last good copy instead
  of an error. Errors themselves are still never stored. No change in
  normal operation.
- `XCP_PAGE_SWR` (off by default) adds `stale-while-revalidate`.
- `scripts/edge_purge.py`: purge Cloudflare after the boards swap (step
  10_edge_purge), at the end of the run (19_edge_purge, then again 16 min
  later, detached, once the workers' own 15-minute board copies have
  expired) and at the end of the nightly update. A no-op until
  `XCP_CF_ZONE_ID` and `XCP_CF_API_TOKEN` are set.
- With the purge configured, `XCP_PAGE_S_MAXAGE` can be raised (see step 8
  below): the TTL stops being the staleness bound, the purge is.
- The workers' board copy (`XCP_BOARD_API_TTL`) now defaults to 900 s on
  its own, so raising the edge TTL never lengthens it.

Run with no pipeline going (CREATE INDEX CONCURRENTLY waits on long
transactions, and a rebuild of `results` mid-build would discard it). Each
`psql` line is one statement per `-c`: CONCURRENTLY cannot run inside the
implicit transaction a multi-statement `-c` makes.

**0. Pull, and look before building.**

    cd /srv/xc-predictor && git pull && set -a; . /etc/xc-predictor.env; set +a
    df -h /var/lib/postgresql
    sudo -u postgres psql -P pager=off -d xc_predictor -c "SELECT t.relname AS tbl, c.relname AS idx, i.indisvalid AS valid, pg_size_pretty(pg_relation_size(c.oid)) AS size, pg_get_indexdef(i.indexrelid) AS def FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid JOIN pg_class t ON t.oid = i.indrelid WHERE t.relname IN ('results','athlete_season') ORDER BY 1, 2;"
    sudo -u postgres psql -P pager=off -d xc_predictor -c "SELECT relname, n_live_tup, n_dead_tup, last_vacuum, last_autovacuum, last_analyze, last_autoanalyze FROM pg_stat_user_tables WHERE relname IN ('results','results_tf','athlete_season','ranking_results');"
