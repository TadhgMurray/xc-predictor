## What was slow, and why

**Over 2 s at the origin on a healthy site:** the PR board (11.6-13.9 s,
every time) and, borderline, `/search` (1.4-3.8 s). **1-2 s:** the ability
board sorted by season best (1.3-1.8 s), the state landing page and the
conference page (0.8-1.2 s). Everything else answered in 0.2-0.6 s at the
origin, athlete and race pages included.

**Why the slow-request mails say 30-60 s for pages that take 0.3 s:**
gunicorn serves one request per worker (24 workers x 3 database connections
since dd0eda5, 8 before). When some requests are slow -- the PR board, a page
during a pipeline run when the cache is cold, an outage -- they hold workers
and connections, every other request waits, and its time is the queue's.
The first sweep showed exactly that: a `400` that does no database work
took 31-33 s.

1. **The PR board** (`board=pr&sport=XC&pool=hs_m&distance=5000`: 11.6-16.9 s
   at the origin, every time; not in the mails, found by the sweep). Its
   candidate step is `pool = ? AND sport = ? AND distance BETWEEN lo AND hi
   ORDER BY time_seconds LIMIT 2000`. A RANGE on distance sits between the
   equalities and the ordering in `rr_pr_sport_time_idx (pool, sport,
   distance, time_seconds)`, so Postgres read every hs_m XC 5K result
   (a parallel sequential scan) and sorted them. **Fix (query only, no
   index):** the range holds a handful of stored values (5000, 4999.9 ...),
   and for each one the index IS in time order; a recursive CTE finds them
   with one probe each, each one's fastest 2000 are read in index order,
   and the fastest 2000 of those are the same candidates. On a 6M-row
   stand-in: 5.4k pages instead of ~207k, identical rows on every board
   tried. `result_id` now breaks ties in that order: two rows at one time
   (an athlete's two races at the same PR) had no order, so which one the
   board kept followed the plan.
   **And a small candidate set first** (`PR_FIRST_FACTOR = 4`): the live
   plan after the rewrite read ~10k pages to fetch 2,000 candidates, which
   held 1,061 athletes for a page of 50. On the default fastest-first order
   the athletes among the N fastest rows are exactly the first athletes of
   the whole list, so when 4x fills the page it is the same page; when it
   does not (deep pages, many-race athletes) the full 40x set runs as
   before. Other sorts re-order the candidates and keep the full set.
   On a 6M-row stand-in, warm: page 1 43 -> 13 ms, page 20 670 -> 46 ms,
   identical rows on every board tried.

2. **JIT compilation on every board query.** Postgres compiles a plan once
   its *estimated* cost passes `jit_above_cost` (100k), and a query over
   ranking_results' 61M rows is estimated that high even when the index
   reads a few thousand pages. Measured on the PR board's new plan: 25 ms
   with `jit = off`, 1,155 ms with it on, every run, all of it compile time.
   That is the likely second in the 1-2 s boards. **Fix:** the website's
   connections carry `-c jit=off` (`XCP_DB_JIT`, which app.py defaults to
   off; the pipeline keeps JIT). Step 0 below shows whether the server has
   JIT on; the plans in step 1 show its time per query.

3. **The ability board sorted by season best** (1.3-1.8 s; 51.8 s in the
   mail, under load). With the year at "Any", the ORDER BY is `best_rating
   DESC NULLS LAST, mean_rating DESC, person_id` after `pool = ? AND sport =
   ?`, and the only best-rating index has `year` in between, so every season
   of the pool is read and sorted for one page. **Fix:**
   `as_pool_sport_best_idx (pool, sport, best_rating DESC NULLS LAST,
   mean_rating DESC, person_id)` and `as_pool_best_idx` (no sport, for
   `sport=both`). On a 2.4M-row stand-in: an Index Scan of 123 pages instead
   of a sort of the pool. The default sort already has its index (0.24-0.42
   s live).

4. **`/athlete/:id`** (0.45-0.6 s healthy; up to 55 s in the mails, during
   pipeline go-lives). The race list counts each race's place over the
   race's whole field, reading `meet_id, div_id, source, time_seconds,
   result_id, status, school`. The index planned for it,
   `idx_results_meet_div_place (meet_id, div_id) INCLUDE (time_seconds,
   school)`, lacks `source`, `result_id` and `status`, so every competitor
   of every race is a heap read -- cheap when cached, tens of thousands of
   disk reads when the pipeline has evicted the cache. Nothing in the
   pipeline vacuumed `results` either, and the go-live rewrites it, so even
   a covering index would fall back to the heap. **Fix:**
   `idx_results_meet_src_cover (meet_id, source, div_id) INCLUDE
   (time_seconds, result_id, school, status)` (index-only, 0 heap fetches on
   a stand-in), and pipeline step 18c vacuums `results` and `results_tf`.

5. **`/race/xc/:meet/:div`** (0.28-0.37 s healthy; 63 s in the mail on
   `SELECT source, count(*) FROM results WHERE meet_id = ? GROUP BY
   source`). `source` lives only in the heap: one read per row of the meet,
   and a race view ran it up to three times. **Fix:** the same index (29
   pages, index-only, on a shuffled stand-in) and `meet_sources` remembered
   per request.

6. **Cache fan-out from `?r=` links.** Every race and XC meet link on an
   athlete page carried `?r=<result id>`. The edge caches by full URL, so a
   race page existed once per finisher who linked to it, every click on one
   was a MISS, and each ran the feed count (three times) only to redirect
   to the plain URL. The pin only matters when two feeds share the meet id.
   **Fix:** the athlete page checks, per race, whether another feed holds
   that meet id (two probes on the new index); if not, the link is the
   plain URL plus `#r<id>`, exactly where the redirect landed. Multi-feed
   meets, and TF meet links (their page reads `?r=` for its scroll
   anchor), keep `?r=`. The check runs only once the index exists, so the
   code deployed first changes nothing.

7. **The site's own slow log (`scripts/slow_log_summary.py --hours 168`),
   by database time per week** -- most of it is not the pages the mails
   named:

   | statement | from | runs > 250 ms | total |
   |---|---|---|---|
   | `min(n_races)` on season_comps | athlete / recruit pages | 104,127 | 55,851 s -- **fixed in 028a8e9** (cached per process) |
   | what it takes: finishers + season ratings | `-` (background threads) | 85,929 | 55,218 s |
   | runners like you: the comps search | `/recruit/:id`, `/api/runners-like-you` | 59,186 | 37,778 s |
   | `grade_fix` lookup, every one 5.00 s | athlete page | 660 | 2,999 s |

   - **What it takes** (cuts.py) fills each state's marks in a background
     thread, per worker, every 6 h: with 24 workers, every state 24 times.
     **Fix:** `racecast/sharedcache.py` -- the first worker computes and
     writes the state's marks to a file (locked, atomic, in a directory
     only the site's user can write); the others read it. A worker keeps
     its memory copy only for what is left of the 6 h, so no state is older
     than before. One compute per state per 6 h for the box.
   - **Runners like you** joined the athlete-name lookup (three subqueries)
     onto every comparable athlete in the band -- 1,534 rows on a stand-in
     -- when only the 5 examples print a name. **Fix:** the band is read
     without names; the 5 examples are named afterwards with the same
     lookup. Identical output on a stand-in.
   - **grade_fix**: `engine/grade_sanity.write` began with `DROP TABLE
     grade_fix` and then copied ~31M rows in the same transaction, so the
     table was locked for the whole copy and every athlete page waited out
     its 5 s lock_timeout and failed. **Fix:** it loads `grade_fix_new` /
     `grade_untrusted_new` beside the live tables and renames them in at
     the very end, a moment before the commit.

Not fixed here: `/search` (0.9-1.0 s after the JIT change, uncacheable by
design).

## Part 5: the 6-hour slow log's worst single statements

`slow_log_summary.py --hours 6 --worst 10 --path /api/rankings`:

- **The events-filtered ability board** (`dist_min=3000`): 55.01 s (the
  statement timeout) for ms_m 2026, 26 s for hs_m CA grade 11. The board
  recomputes seasons from ranking_results; its median was a GROUP BY over a
  CTE joined back to the CTE, and the planner, unable to estimate a CTE,
  guessed ~34 rows against ~900k and planned a nested loop -- every season
  against every race. **Fix:** the median by window functions in one
  sorted pass (the mid-point of the middle race or two, which is
  percentile_cont(0.5) exactly -- proved group by group on Postgres), the
  outlier cut on the row, and only the columns the aggregate reads. Same
  boards on every variant tried; a 2M-row stand-in went from past ten
  minutes to 8 s. What is left is the aggregate itself (~350k seasons, a
  quantile and three modes each); under 2 s needs the four presets
  (800 / 1500 / 3000 / 5000 and up) precomputed in step 10 -- not done.
- **The PR board on pool=all**: 4.7-7.6 s. The per-distance walk needed a
  pool; it now walks the pools too (each the next pool after the last, one
  probe), then each pool's stored distances; a row with no pool is read by
  its own branch, so the set cannot differ. Stand-in, warm: 612 -> 9 ms,
  same rows.
- The grade_fix lookups at exactly 5.00 s (323 in 6 h) are a pipeline run's
  old grade_sanity write; the next run uses part 3's shadow write.

  10f4_season_events, nightly 10f4): the four Events presets (800, 1500,
  3000, 5000 and up) precomputed with _abilitySource's own query over every
  pool, sport and year at the default scope (US races). A board reads it
  only when nothing else picks races (no state, school, grade, unit,
  scope or dist_max -- rankings._evPreset) and only while it was built
  from the live ranking_results (the table's comment names that table's
  oid -- rankings._evTableFresh); every other board, and the team board,
  runs live. Same rows, counts and rank lines as the live query on every
  board tried. Stand-in build: 4.8M seasons in 52 s on 4 workers.
- **athlete_season_ev_grade** (2026-11-08, the same script and step, built
  after athlete_season_ev): one grade. A grade filter picks races by each
  race's grade key, so the grade-10 board is a different season; this table
  is the same query with the key added to every window partition and the
  GROUP BY (_abilitySource(by_grade=True)). A board with ONE grade key
  (rankings._evGradePreset; several grades run live) reads it while its
  rr_oid stamp is live. Stand-in (2.1M races): grade-10 1500m+ board 2.7 s
  live, 10-14 ms from the table; build +5% time, +13% rows over the plain
  table. XCP_SEASON_EV_GRADE=0 or --only ev skips it.
- **prewarm** (scripts/prewarm.py; pipeline 19b_prewarm after the vacuum,
  nightly 13z_prewarm): pg_prewarm reads the board tables' indexes, then the
  smaller tables, into the page cache after every swap, capped at
  XCP_PREWARM_GB (16). After it, a cold first request runs at warm speed on
  the stand-in (ability sort=best 12-13 ms).

Server time with compression (what a browser waits for): search 1.0-1.3 s,
home page 1.1-1.3 s when the edge refills it (it is otherwise a HIT),
conference and state landing pages ~0.8 s, everything else 0.2-0.4 s.

## Caching headers

Headers were already right (no Set-Cookie, `Vary: Accept-Encoding`, pages
and board APIs public with `max-age=300, s-maxage=900`; the edge does HIT
them). What kept the hit rate low: a 15-minute edge TTL over a very long
tail of URLs, the `?r=` fan-out above, and slow origin answers that time
out (a 504 is never stored).

- `stale-if-error=86400` on every public response: when gunicorn times out
  or the swap's 503 is up, Cloudflare may serve the last good copy instead
  of an error. Errors themselves are still never stored. No change in
  normal operation.
- `XCP_PAGE_SWR` (off by default) adds `stale-while-revalidate`.
- `scripts/edge_purge.py`: purge Cloudflare after the boards swap (step
  10_edge_purge), at the end of the run (19_edge_purge, then again 16 min
  later, detached, once the workers' own 15-minute board copies have
  expired) and at the end of the nightly update. A no-op until
  `XCP_CF_ZONE_ID` and `XCP_CF_API_TOKEN` are set.
- With the purge configured, `XCP_PAGE_S_MAXAGE` can be raised (see step 8
  below): the TTL stops being the staleness bound, the purge is.
- The workers' board copy (`XCP_BOARD_API_TTL`) now defaults to 900 s on
  its own, so raising the edge TTL never lengthens it.
