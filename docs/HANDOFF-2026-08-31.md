## 1. What to run, in order

The pipeline's stage list is `clean · weather · backfill · engine · suspects`.
`--from backfill` skips the weather refit (the heavy stage; only re-run it
when you actually want to refit the curve).

**Suspects is a diagnostic, not a build step**, and `--only` cannot express
"everything except the last one". So run the two build stages and stop:

```
sudo -u xcp bash -lc 'set -a; . /etc/xc-predictor.env; set +a; cd /srv/xc-predictor && \
  setsid nohup /srv/venv/bin/python -u scripts/pipeline.py --sport XC --only backfill \
  > /srv/xc-predictor/pipeline_backfill.log 2>&1 < /dev/null &'

# when that prints PIPELINE COMPLETE:
sudo -u xcp bash -lc 'set -a; . /etc/xc-predictor.env; set +a; cd /srv/xc-predictor && \
  setsid nohup /srv/venv/bin/python -u scripts/pipeline.py --sport XC --only engine \
  > /srv/xc-predictor/pipeline_engine.log 2>&1 < /dev/null &'

# then the boards -- NOT a pipeline stage, which is why they are always stale:
sudo -u xcp bash -lc 'set -a; . /etc/xc-predictor.env; set +a; cd /srv/xc-predictor && \
  setsid nohup /srv/venv/bin/python -u racecast/build_ranking_results.py --sport both \
  > /srv/xc-predictor/rankings.log 2>&1 < /dev/null &'

sudo systemctl restart xc-predictor
```

✓ `--only` HANDLES `<table>_old` COMPLETELY -- no manual cleanup needed. Both
guards live INSIDE the per-stage loop, so they fire however many stages are
selected: BEFORE a merge stage, a leftover `<table>_old` is verified against
the PREVIOUS merge stage's column and dropped (and `sys.exit` if it fails
verification, rather than continuing); AFTER a merge stage, it verifies and
drops its own. `pipeline.py:295` and `:309`.

! WHAT `--only` DOES SKIP is just the OTHER stages -- weather, and suspects.
  That is the point of using it. Nothing about the old-table bookkeeping is
  conditional on the stage list.

★ **THE BOARDS ARE NOT IN THE PIPELINE.** `build_ranking_results` is a
separate command, which is why #37, the unit columns and `school_state` have
never taken effect. Every pipeline run leaves the site's boards behind.
Fixing that -- adding a `rankings` stage -- is the single highest-value
change to the runner.

**Checking on a run:** `pgrep -af <script> || echo "NOT RUNNING"`, then read
the log for `[all] TOTAL` / `PIPELINE COMPLETE`. `pgrep` alone cannot tell a
finished job from a killed one; the log can. Always launch with
`setsid nohup ... &` and `python -u`, or output buffers and an ssh drop kills
the job.

## 2. Where I actually landed on the engine

I came into this arguing for a rewrite. **Having read the engine, I no longer
think the model is the problem, and I want to be plain about changing my
mind.**

**The model form is right.** `ln(t) = α[athlete,season] + δ[cell]` is how
times actually behave. Identifiability is handled properly — the gauge is
pinned, recentring is derived rather than guessed, connectivity is measured
by three separate tools. CG converges to 9e-11. The corrections are
individually well-fitted and honestly documented; `ability_slope` and
`tilt.py` are better work than I first credited.

**The one concrete hypothesis we tested came back negative.** The distance
fade is barely ability-dependent — spread 0.025 on hs_m against a predicted
0.15, and it *reverses sign* between XC and TF. That killed my "one fault,
four symptoms" story (#71). Do not resurrect it without new evidence.

**What is actually broken is artifact management.** Look at every real bug
found on 2026-08-30/31 and notice they are one shape:

- `bbar` measured at ridge 0, applied to a ridge-0.5 solve — frozen since
  Aug 26, sign flipped, nobody noticed (#73)
- the feedback loop that maintains it is documented in detail and **does not
  exist** (#74)
- `--validate` scored a model nobody fitted, and had already cost the
  `--tilt` feature on that bad evidence (#72)
- τ² comes back **negative** and silently falls back (#75)
- `age_band_result` built, read by nothing (#47)
- `diag_exponent_by_ability` never run, holding the answer to a live question
- `--split` shipped at the wrong ridge because a sweep was run and not acted
  on (#70)

Not one is a modelling error. Every one is a piece of state that went stale,
was never consumed, or was applied under conditions it was not measured for.
**The engine is ~15 independently-maintained artifacts with nothing checking
they are mutually consistent.** A new model inherits that whole.

### What I would build instead of a rewrite

1. **Provenance on every artifact.** Each `.pkl`/`.json` records the code,
   the data and the PARAMETERS that produced it — the ridge above all.
   Consuming one whose parameters do not match the current run is a hard
   stop. That is the `bbar` guard shipped today, generalised.
2. **One command that fits and applies together.** `bbar` drifted because
   fitting and applying are different scripts run at different times. If they
   cannot be run apart, they cannot drift apart.
3. **Invariants that fail loudly.** A variance cannot be negative. A
   validation must fit what the run fitted. An artifact older than its inputs
   is stale. Each is a few lines; each would have caught a real bug today.

### On the joint model

Still worth doing eventually — but **the honest reason is operational, not
statistical**. One solve with every term inside it makes staleness impossible
because there are no artifacts to go stale. That is a better argument than
"the math is better", which I overstated and cannot back with a measured
fault. Endgame, not next step, and it needs the three items above underneath
it regardless.

⚠ WHY IT IS HARD TO ANSWER AFTER THE FACT, and the lesson for next time: the
engine stage rewrote `speed_rating` wholesale with **no diff recorded** —
`merge_column` drops its own `<table>_old` before the pipeline's guard can
compare it. So there is no before/after. **Run the next pipeline with
`--keep-old`** and diff deliberately. That is #78, and it is the single change
that would make this answerable.

### The ladder, most-likely-culprit first

Each rung needs a **backfill + engine re-run** to take effect — reverting the
code alone changes nothing already written to `results`.

**Rung 1 — `39c6ec3` (#47 wiring). The highest-risk change I made.**
It rewrote the SQL the engine reads through, in three files:
`backfill_normalize._streamSQL` (table aliased `r`, grade wrapped in a CASE),
`speed_ratings_db` (both pack queries), `grade_sanity` (the allraces build).
It is *designed* to be a byte-for-byte no-op when `age_band_result` is absent,
and that table has never been written — but it is the only commit that touched
the hot read path, and column-order verification was done against a stub, not
the real schema.

```
git revert --no-edit 39c6ec3
```

**Rung 2 — `1e1272b` (Huber reweighting).** `ROBUST_C = 0`, so it is off and
cannot change a number. Revert only to eliminate it as a variable.

```
git revert --no-edit 1e1272b
```

**Rung 3 — the intentional behaviour changes.** These DO move ratings, by
design and by request, and reverting them undoes work that was wanted:
`edc0a53` / `6c2dcfe` (#14, chair athletes excluded by PERSON — removes 481
athletes' races from the solve entirely), `592cd33` (no normalized time means
no rating). If the fault is here it is a *scope* disagreement, not a bug.

**Not in the blast radius at all** — `pair_all` / `pair_validate` changes
(`--split`, the bbar guard, the validation fix) only run under `--split`, which

### Before reverting anything, check #79 directly

The Apalachee number may be a thin or unidentified cell rather than a
regression. Its 8000m cell at a venue that mostly hosts NCAA and USATF races
could be carried by a single junior race, and an unidentified cell can sit
anywhere along its ray — with the ridge *hiding* that by pulling it toward a
prior instead of flagging it. Check the cell's degree and row count, whether
Apalachee's other distances agree, and `diag_connectivity` / `component_check`
on it. If 5000m there is near zero and only 8000m is −0.144, the fault is one
cell, not the engine.
