## 1. THE ONE THING THAT MATTERS: #104

### What was wrong

`normalize_distance.targetFor(pool, sport)` exists so a caller can reason
about **what scale a `normalized_time` is on**. The artifact carries both
bare and sport-suffixed anchors:

```
pool_targets["hs_m"]      = 5000        pool_targets["hs_m|TF"]  = 1600
pool_targets["ms_m"]      = 3200        pool_targets["ms_m|TF"]  = 1600
pool_targets["elem_m"]    = 2414        pool_targets["elem_m|TF"]= 1200
pool_targets["college_m"] = 8000        pool_targets["college_m|TF"] = 3000
```

`targetFor` preferred the **suffixed** key. The normaliser does the exact
opposite — `_normalizeWithPotential` **strips the suffix deliberately** (its
own comment says so) and reads the bare key:

```python
base   = (pool or "").split("|")[0]          # "hs_m", never "hs_m|TF"
target = (_SPLINES["pool_targets"].get(base)     # 5000  <- always wins
          or entry.get("target")                 # 1600, never reached
          or _SPLINES["target"])
```

So **`pool_targets["hs_m|TF"] = 1600` has never been applied to a single row
in the database.** Every high-school track result is stored as a
5000m-equivalent. Every caller that asked what scale it was on was told 1600.

`poolBandFor` multiplies that anchor by `PACE_FLOOR`/`PACE_CEIL` (0.12 and
0.72 s/m — 2:00/km and 12:00/km). So the sanity band came out as a 1600m band
applied to 5000m numbers.

### Which call sites actually got it

This is the part that decides how bad it is, and it turns on **whether the
caller passes `sport=`**:

```
07_pack   speed_ratings.py --sport merged
          poolOf(merge=True) returns the BARE pool "hs_m"
          poolBand(pool) passes NO sport
             -> targetFor("hs_m")       = 5000   band (600, 3600)   CORRECT

10_rankings  build_ranking_results.py
          pool is bare too (resolvePool merge=True), but it PASSES sport="TF"
             -> targetFor("hs_m","TF")  = 1600   band (192, 1152)   WRONG

per-sport runs  speed_ratings.py --sport TF
          poolOf(merge=False) returns "hs_m|TF", suffix read off the pool
             -> targetFor("hs_m|TF")    = 1600   band (192, 1152)   WRONG
```

★ **THE POOL MEAN IS SAFE, AND THIS IS THE HEADLINE.** The production solve
is step 07 (`--sport merged`) feeding step 08. It passes no sport, got the
correct band, and therefore saw the whole field. `alpha`, `ability` and
`pool_mean` were all computed over everybody. **No rating was rebased against
a too-fast mean.** An athlete's number on their own page is what it always
was.

⚠ **THE BOARDS WERE TRUNCATED.** `ranking_results` refused every
high-school track row above 1152s. Those rows still carry their ratings in
`results.speed_rating` — they were denied a leaderboard place, not corrupted.

⚠ **AND THE FLOOR NEVER FIRED.** 192s as a 5000m-equivalent is impossible, so
nothing could fail it, where XC's floor is 600. That is the leak that let
impossibly fast track rows onto boards untouched.

```
  4:20 -> norm  912   ok         9:10 -> norm  889   ok       1:55 -> norm  901  ok

  7:00 -> norm 1472   DROPPED   14:30 -> norm 1406  DROPPED   3:05 -> norm 1449  DROPPED
```

The cut, per pool:

```
  hs_m   slower than 2:27.5 / 800, 5:29.0 / 1600, 11:53.0 / 3200  -> no board
  hs_f   slower than 2:28.5 / 800, 5:31.0 / 1600, 11:54.5 / 3200  -> no board
  ms_m   slower than 4:04.0 / 800, 8:55.5 / 1600  (barely bites)
```

⚠ **THE SAME ABSOLUTE CUT FOR BOTH GENDERS.** Girls are slower on average, so

asymmetry matters in section 2.

### The fix

`targetFor` now reads the bare pool first, exactly as the normaliser does,
and falls back to a suffixed anchor only when the bare pool has none (so an
older artifact carrying only suffixed keys still resolves). Commit `0c96392`.

The invariant that makes the function mean anything is now tested
(`tests/test_sport_gap_knob.py`):

- **`normalizeTime` must be the identity at the anchor it reports.** A 600s
  race at `targetFor(p, sp)` must normalise to 600s.
- **One pool has one anchor across both sports**, because `alpha` is a single
  ability per athlete-season spanning fall XC and spring track.
- The band follows, and an ordinary 6:00 1600 must be inside it.

Reverting the fix fails that test on **all eight pools**, both genders.

See section 4.

## 2. CURRENT METHODOLOGY — how a rating is made, and where #104 sat in it

Read this before touching the engine; the bug above is only legible against it.

### The chain

```
  raw time
    |  normalize_distance.normalizeTime(t, d, pool, sport)
    |     T_anchor = T_d * exp( g(ln target) - g(ln d) )
    |     g is a per-(pool,sport) 1-D potential; target is PER POOL (bare).
    v
  normalized_time                      <- an anchor-distance-equivalent time
    |  speed_ratings.packResults: pool, sanity band, pack to .npz
    v
  the solve   linkage_check.py --golive --split
    |     ln(t) = alpha[athlete,season] + beta[athlete,season]*s + delta[cell]
    |     alpha = ability, one per athlete-season, spanning BOTH sports
    |     beta  = that athlete's own XC-vs-TF offset
    |     delta = cell difficulty; a cell is  XC:<venue>:d<dist>
    |     ridge 0 -- the sport direction is then EXACTLY null, so CG never
    |               enters it and the rest is well conditioned
    v
  recenterSport(D)  -- pair_recenter.recenter
    |     beta -= bbar ; delta += bbar*s_c ; alpha -= bbar*sbar_g
    |     A REPARAMETERISATION: every prediction is unchanged. It moves the
    |     mean sport offset out of beta (where it is unidentifiable against
    |     the XC/TF level) and into the difficulties.
    v
  ratings   pair_ratings.buildRatings
    |     rating_seasonal = 100 * mean_ability(pool, season) / ability
    |     rating_career   = 100 * mean_ability(pool)         / ability
    |     anchor set is races >= 3; rated set is races >= 2
    v
  results.speed_rating   (per race: 100 * pool_mean / (norm / exp(delta)))
    v
  ranking_results        <- the BOARDS. A SECOND gate lives here.  #104
```

### The three ideas you must hold to read any of this

**1. A rating is pool-relative.** 100 is the mean of *your* pool. Ratings are
not comparable across pools without `pool_view.repFactor`. That is why #103
existed (a squad picked by sorting hs and ms ratings together).

**2. The sport gap is an identification problem, not a bug.** The per-athlete
sport offset and the XC-vs-TF difficulty level are *the same parameter*. The
operator's eigenvalue along "+1 on every TF cell, −1 on every XC cell":

```
    shared ability   90.81        ridge K=1   26.75
    ridge K=5        60.46        full split   0.00
```

A world where every runner is 4% slower on grass and a world where grass is
4% harder produce identical times. `recenterSport` resolves it by *assuming*
specialisation averages out across athletes — stated, not measured. Without
it, minimum-norm CG silently asserts XC and TF have **equal** mean difficulty,
which is certainly false.

**3. `bbar` is maintained by a nightly feedback loop, through a file.**

```
  08_golive   applies data/sport_gap_bbar.json:measured_bbar,
              records applied_bbar
  10c_gap     measure_sport_gap.py --emit reads ranking_results,
              measures D on the fresh ratings,
              writes measured_bbar = applied + D
```

D converging toward 0 across nights is the loop working. It has converged:
**global D = +0.00006**, `measured_date 2026-09-01`. Delete the file to fall
back to the solve's own estimate.

### How the sport gap is measured — the sandwich

`scripts/measure_sport_gap.py`. Inside an athlete-season the sport contrast is
**perfectly collinear with time**: `season_year` opens the academic year in
August, so one group holds fall XC and the *following* spring's track, XC
first. A kid who is fitter in spring produces a signal identical to "track is
easier", and nothing inside a group can separate them.

So the estimator refuses to use the solve's grouping. It puts the XC season
**between two TF seasons** and interpolates the athlete's own level across it
by date:

```
    w    = (t2 - t1) / (t3 - t1)
    lhat = ln r1 + w * (ln r3 - ln r1)
    d    = ln r2 - lhat
```

Any monotone improvement cancels. Both directions are always run: TF-XC-TF
returns C + D and XC-TF-XC returns C − D, so their **mean is D with curvature
removed exactly** and half their difference *is* the curvature.

★ **THE GROWTH HYPOTHESIS IS DEAD, AND THE NUMBER THAT KILLED IT IS WORTH
KEEPING.** If growth were in `bbar` the two would disagree:

```
    bbar in the engine     -0.03924
    sandwich (growth-free) -0.03878        1.2% apart
```

⚠ **WHAT THE SANDWICH STILL CANNOT REMOVE: the seasonal cycle.** Interpolating
between two springs and evaluating at the intervening fall confounds "track is
easier" with "athletes peak in spring". Those are the same contrast,
observationally. Neither estimator separates them, and there is a fair
argument part of it *belongs* in sport difficulty — a track PR is run in peak
condition on a fast surface. What is ruled out is a freshman's eight months of
growing up.

### What the per-pool split found, and why per-pool bbar is NOT the fix (#106)

`--by-pool` shows the global D near zero while the pools disagree and cancel:

```
    hs_f   -0.01899          ms_m   +0.01658
    elem_f -0.01439          hs_m   +0.00257
```

The obvious move is "give each pool its own bbar". **It cannot be done, and
the reason is the cell key.** `bbar` reaches ratings through
`delta_c += bbar * s_c`, and a cell is `XC:<venue>:d<dist>` — namespaced by
sport and distance, **not by pool**. `hs_m` and `hs_f` racing the same 5000m
at the same venue *share one delta*. The identity

```
    alpha -= bbar*sbar_g ;   beta -= bbar ;   delta += bbar*s_c
```

only cancels because it is the same `bbar` in all three places. Make the first
per-pool and the third cannot follow, so predictions stop being preserved —
which is the entire argument for recentring being safe.

★ **AND THE MEASUREMENT AGREES.** Splitting D into its halves across eight
pools (`--from rating` vs `--from norm`):

```
    D(cell)   mean +0.0538,  sd 0.0024     <- what bbar controls: FLAT
    D(norm)   mean -0.0362,  sd 0.0151     <- ALL of the pool spread
```

The cell half is the same in every pool — exactly what one global constant
deposited in every cell should look like. **`bbar` is behaving.** Every bit of
the pool variation is in the *normalisation*.

⚠ The distance-curve story is not proven either: `D/span` spread is **415% of
its mean**, so D does not track the distance span and a single exponent error
does not explain it. What is established is only where the spread **isn't**:
not in the cells, so not in `bbar`.

`recenter()` now raises on a non-scalar `bbar` with that reason, because an
array would have *broadcast* against `s_cell` rather than failing. The whole
argument is written up beside `MEASURED_BBAR` in `engine/pair_recenter.py`.

### ★ HOW #104 FEEDS BACK INTO RATINGS — the one real leak

`measure_sport_gap` reads **`ranking_results`**, the table #104 truncated. So:

```
  10_rankings  builds a TF sample missing everyone slower than ~5:29/1600
  10c_gap      measures D on that sample, writes measured_bbar
  08_golive    next night, applies it to every cell
```

The mechanism is **athlete selection, not a shifted mean**: a sandwich needs
three blocks, so dropping an athlete's slow TF blocks removes that athlete
from the estimate entirely. D is measured only on athletes fast enough in
track to clear the cut. The XC-vs-TF discrepancy is known to vary with ability
— that is the fitted tilt, `_TILT_K = -0.031` per 10 rating points — so
selecting on TF ability can bias D, **by an amount that differs per pool with
how hard the cut bites.**

That is a candidate explanation for the per-pool spread above: the pools whose
track tail was cut hardest read most negative (`hs_f` −0.019), and `ms`, where
the cut barely bites, reads most positive (+0.017). **It is a mechanism, not a
measurement** — it needs the rebuilt table to test.

Scale: `bbar` has converged (global D +0.00006), but converged against a
truncated sample. How far it moves once the boards are rebuilt is unknown; the
per-pool D's of ±0.02 put a rough ceiling at ~2% in log-rating, about 2.6
points at a 130. Global and common-mode, not per-athlete.

! `fill_ratings` also reads `ranking_results` — the per-pool median of
  `speed_rating * normalized_time`. That product is near-constant per pool by
  construction so truncation should not bias it, but it "carries the row's
  difficulty adjustment" and so is not *exactly* constant. Take that constant
  before and after rather than assuming.

### What Mt. SAC vs the 9:01 is NOT

The owner's standing test case:

```
  2024-10-26  Mt. SAC     4828m XC   15:40   -> 133.7  (+0.067)
  2025-04-12  Arcadia     3200m TF    9:01.1 -> 133.6  (-0.044)
```

- **Not the sport offset.** `hs_m`'s D is +0.00257 ≈ 0.35 rating points at

## 3. WHAT TO RUN

### 3a. The pipeline

`deploy/run_pipeline.sh` — 26 steps, **four hours**, run it under tmux or it
dies with your ssh session.

```
  bash deploy/run_pipeline.sh                  # everything
  bash deploy/run_pipeline.sh --from 10        # rankings and after
  bash deploy/run_pipeline.sh --skip-backfill  # corrections/rules unchanged
  bash deploy/run_pipeline.sh --dry-run        # print the plan, run nothing
```

★ **FOR #104, `--from 10` IS THE RIGHT RUN.** It rebuilds `ranking_results`
(step 10) and then re-runs `measure_sport_gap --emit` (10c) against the fixed
table, in that order. A full run is not needed — the solve was never wrong.

⚠ **PREFLIGHT KILLS RUNS.** `engine/corrections.py` is **not in git**, is
~165MB, and does not crash anything when absent — it silently un-applies every
correction and you find out four hours later from the boards. The script now
hard-stops if it is missing or under 100MB. A `git pull` or a truncated `scp`
will do this.

**Checking on a run:** `pgrep -af <script> || echo "NOT RUNNING"`, then read
the log for `PIPELINE COMPLETE`. `pgrep` alone cannot tell a finished job from
a killed one; the log can. Always `setsid nohup ... &` with `python -u`, or
output buffers and an ssh drop kills the job.

### 3b. Feature extraction → training

**Where things stand.** The owner no longer has the 7900XTX; a ~5-day run is
stranded on an unreachable PC. Feature extraction is running **on the server**,
logging to `/srv/extract.log`. Training will run on a **rented RunPod pod**
(RTX 3090, 32 vCPU, CUDA confirmed). The owner is on a *separate laptop* from
the dead PC — `model/data` has never existed on the laptop, so **every
transfer is server → pod**, never laptop → anywhere.

**Step 1 — is extraction done?**

```
  tail -f /srv/extract.log
  # progress lines read:  "... N chunks, M skipped"
  # the last line is:     "Done. <total>,  examples saved in <N> chunks."
```

`model/feature_extraction.py` writes to `model/data/`: `chunk_NNNN.pt` at
`CHUNK_SIZE = 10_000` examples each, plus metadata. Chunks are **corpus-wide
shuffles**, so a prefix is a fair sample — that is what `--max-chunks` is for.

Count what landed: `ls model/data/chunk_*.pt | wc -l`, and confirm it matches
the metadata's chunk count. A short count means the run died mid-flush.

**Step 2 — server → pod.**

```
  scp -P <pod_port> -r /srv/xc-predictor/model/data/ \
      root@<pod_ip>:/workspace/xc-predictor/model/
```

The pod's ssh is `<ip>:<port>` from the RunPod console. Password auth worked
where the key did not.

**Step 3 — smoke run BEFORE the real one.** Never start a multi-hour train
without proving the loop turns:

```
  python -u model/train.py --max-chunks 5 --batch 512 --amp --workers 8 \
      --checkpoint model/data/ckpt.pt
```

Read the throughput line it prints (`examples_per_s`, `steps_per_s`,
`waiting`). **`waiting` is the number that decides `--workers`**: if the GPU
is waiting, raise it. With `--workers 0` the GPU waits on every disk read.

**Step 4 — the real run.**

```
  setsid nohup python -u model/train.py \
      --batch 512 --lr <scaled> --amp --workers 8 --patience 3 \
      --checkpoint model/data/ckpt.pt \
      > /workspace/train.log 2>&1 < /dev/null &
```

- `--amp` is bf16 on CUDA; no `GradScaler` needed, no-op on CPU.
- `--batch 512–1024` suits 24GB. **Scale `--lr` with the batch.**
- `--patience 3` / `MIN_DELTA 1e-4` — early stopping usually beats the
  `--epochs 20` ceiling.
- ⚠ **`--checkpoint` IS NOT OPTIONAL ON A RENTED POD.** `model.pt` alone
  cannot resume: it has no optimizer state, so Adam's moments restart from
  zero and the first epoch after a resume is worse than the one before it.
  The checkpoint writes weights + optimizer + epoch atomically via
  `os.replace`.

**Stopping a `nohup`'d run:** `pgrep -af train.py` then `kill <pid>`.
`pkill -f train.py` if you mean all of them. Re-pull and relaunch with the
same `--checkpoint` and it picks up where it left off.

### The standing methodology worry, unchanged from 2026-08-31

Every real bug found on 30/31 August and again today is **one shape**: not a
modelling error, but a piece of state that went stale, was never consumed, or
was applied under conditions it was not measured for. #104 is the purest
example yet — two functions in the *same module* disagreeing about what a
number means, for months, with a docstring in one of them warning about
exactly that failure in the opposite direction.

The three things worth building, in order, still stand:

1. **Provenance on every artifact** — code, data and *parameters* that
   produced it; consuming a mismatch is a hard stop.
2. **One command that fits and applies together** — `bbar` drifted because
   fitting and applying are different scripts run at different times.
3. **Invariants that fail loudly.** A variance cannot be negative. A
   validation must fit what the run fitted. **`normalizeTime` must be the
   identity at the anchor it reports** — that one is now written down and
   tested, and it is the whole of #104.
