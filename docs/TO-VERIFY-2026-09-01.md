exercised against the running site** -- there is no browser and no database

reasoning holds", not "it works".

test that runs without a database, which is most of the logic -- the risk is
concentrated in the DOM, the CSS, and the SQL.

## Needs a rebuild before it takes effect

- [ ] **The TF sanity band was the anchor for the wrong distance.**
      `targetFor` preferred the artifact's `hs_m|TF` = 1600 while the
      normaliser (`_normalizeWithPotential`) strips the suffix and uses
      `hs_m` = 5000. So `poolBandFor` gated high-school track at
      (192, 1152) -- a 1600m band applied to 5000m-equivalent numbers.
      Fixed in `normalize_distance.targetFor`; the invariant is now tested
      (`tests/test_sport_gap_knob.py`): normalizeTime must be the identity
      at the anchor it reports.

      Nothing changes until `ranking_results` is rebuilt. When it is, expect:
      - **Boards gain rows.** Every hs TF result slower than about 5:29/1600,
        11:53/3200 or 2:27/800 was refused a place. Same absolute cut for
        both genders, so hs_f lost proportionally more than hs_m.
      - **Boards lose a few.** The TF floor rises 192 -> 600, which is the
        first thing that has ever been able to reject an impossibly fast
        track row.
      - Measure it first: `_GATE['TF']['outside_band']` per pool before and
        after, or just
        `SELECT pool, count(*) FILTER (WHERE normalized_time > 1152)
         FROM ... WHERE sport = 'TF' GROUP BY pool`.

- [ ] **Re-run `measure_sport_gap --by-pool` afterwards.** It reads
      `ranking_results`, so the per-pool D spread (hs_f -0.019, ms_m +0.017)
      was measured on a TF sample truncated differently in every pool. Those
      numbers are not trustworthy until the boards are rebuilt.
