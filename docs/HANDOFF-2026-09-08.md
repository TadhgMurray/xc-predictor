## 1. THE OUTAGE OF 2026-09-07 AND WHAT NOW STANDS BETWEEN THE PIPELINE AND THE SITE (issue 300)

The site was a 500 for hours. `FATAL: sorry, too many clients already`
and even psql could not connect (the site connects as the superuser,
so the reserved slots were gone too). From the OS side nine live
sockets; from Postgres ninety backends, all `SELECT waiting`, clients
gone. The chain: 09b_fill read pool constants on one pooled
connection and left that transaction open (ACCESS SHARE on results);
the writer, on a second pooled connection, opened with `ALTER TABLE
results ADD COLUMN IF NOT EXISTS rating_pool`, which takes ACCESS
EXCLUSIVE even when the column exists, and waited on the first
forever (a deadlock across two connections of one process, invisible
to Postgres because the holder is idle). Every site SELECT on results
queued behind the ALTER; gunicorn killed each worker at `--timeout
60`, the backends lived on, ninety of them filled `max_connections =
100`. Recovery: SIGTERM to every backend whose client port had no
live socket (the pg_terminate_backend equivalent from the shell),
then kill the fill.

Then the athlete page alone was a 500: the pool handed out a
connection whose backend had been terminated and never noticed.
Then 500s in pairs: the rerun's swap siege terminates the backends
that block it (by design, rounds 15..20) and the page in flight
failed.

What now stands, in layers, so no single one has to hold:

- `engine/fill_ratings.py` commits before the writer runs and again
  when its named cursor closes.
- `engine/speed_ratings_db._ensureRatingPool` reads
  information_schema first and ALTERs only when the column is
  missing, under a 5 s lock_timeout, six tries.
- `build_ranking_results._migrateLive`: step 10's dozen live-table
  ALTERs, same treatment, committed before the shadow build.
- `scripts/build_college_directory.py --write`: the swap waits five
  seconds at a time, names the holder, gives up cleanly.
- `racecast/search_index.py`: the swap waits five seconds at a time.
- `scripts/database.py`: the site's connections (and only the site's:
  the unit sets the environment) get `lock_timeout` 5 s,
  `statement_timeout` 55 s (under gunicorn's 60), a pool of 1..6 per
  worker (8 x 6 = 48 of 100) and `application_name=site`. The drop-in
  the owner installed:

  ```
  /etc/systemd/system/xc-predictor.service.d/db.conf
  [Service]
  Environment=XCP_DB_APP=site XCP_DB_MIN_CONN=1 XCP_DB_MAX_CONN=6
  Environment=XCP_DB_LOCK_TIMEOUT_MS=5000 XCP_DB_STATEMENT_TIMEOUT_MS=55000
  ```

  `deploy/server_setup.sh` writes the same into the unit for a fresh
  box. The pipeline keeps the defaults (5..250, no timeouts).
- `getConn` probes a connection with `SELECT 1` before handing it out,
  discards a dead one, and closes rather than returns one that broke.
- `racecast/app.py`: a database blip on a GET is retried once on a
  fresh connection inside the request; a second failure is a branded
  503 with Retry-After; a 500 of any other kind renders
  `templates/error.html` (the topbar, the search box) for pages and
  the raw status for /api and /card callers.
- `engine/maintenance.siteMaintenance` drops
  `/var/tmp/racecast-maintenance` around both table swaps
  (`merge_column._swapSiege`, `build_ranking_results` swapIn); while it
  exists every page is a 503 with Retry-After: 120, so a crawler keeps
  the page and comes back.

Not built: a health URL with a systemd timer; an outside monitor
(UptimeRobot, five minutes of the owner's time). Both offered, neither
asked for.

The sweep for orphaned backends, when it is needed again (rebuild the
port list FIRST; a stale list took live site connections once):

```
ss -tn state established '( sport = :5432 )' | awk 'NR>1{split($4,a,":"); print a[length(a)]}' | sort -u > /tmp/live_ports
ps -eo pid,cmd | grep 'postgres: ' | grep -v grep | grep -E '127\.0\.0\.1\([0-9]+\)' | while read pid rest; do
  port=$(echo "$rest" | grep -oE '\(([0-9]+)\)' | tr -d '()' | tail -1)
  grep -qx "$port" /tmp/live_ports || { echo "orphan $pid: $rest" | cut -c1-110; kill -TERM "$pid"; }
done
```

## 4. THINGS THAT BIT, SO NOBODY REPEATS THEM

- **`XCP_JOINT_LIVE` off the command line put the old engine live for
  two days and nobody noticed.** Now the default. Always check the
  go-live log for `winter gain per band` (joint) versus `[link]` (old).
- ADD COLUMN IF NOT EXISTS takes ACCESS EXCLUSIVE even when the column
  exists. Never run one blind while the site is up; look first, lock
  timeout, commit alone.
- A pooled connection whose backend died is handed out again unless
  the pool checks. It checks now.
- The go-live writes `rating_pool` as `pool|sport`; the fill writes the
  bare pool. A probe that filters on the bare name samples only filled
  rows (that was my second withdrawn verdict).
- Banding a same-athlete gain on one season's rating reads regression
  to the mean as a gain at the bottom and a loss at the top. Band on
  the pair's average.
- `explain_joint_row.py` needs the pack the solve saw; a pack rebuilt
  after the solve fails with "does not fit this pack".
- `pkill -f <pattern>` from a shell whose command line contains the
  pattern kills the shell (exit 144).
- A `for`/`else` re-indent by script: check the loop's tail after.
- The scratchpad render script overwrote a card render I then sent
  three times as if new. Render to a fresh filename, open the file
  before sending.
